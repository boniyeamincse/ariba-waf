# Ariba Shield WAF — Management API Specification

**Version:** 0.1.0 draft  
**Date:** 9 November 2026  
**Implementation:** Go, SQLite, Nginx + ModSecurity v3 + OWASP CRS  
**Architecture:** `ariba-shield-waf-architecture.md`  
**Status:** Proposed contract for development. Only the internal liveness/readiness probes are implemented; management endpoints are not deployed.

## 1. Scope and base URLs

The API manages the single-container Ariba Shield WAF through its dedicated management listener.

| Environment | Browser-facing base URL | Internal API |
| --- | --- | --- |
| Local development | `http://localhost:3000/api/v1` through the frontend development proxy | `http://127.0.0.1:9000/api/v1` |
| Packaged container | `https://localhost:9443/api/v1` | `http://127.0.0.1:9000/api/v1`, not published |

Use relative `/api/v1` URLs in the dashboard. Production dashboard assets and API share the management origin. Protected website listeners must never route requests into this API. A protected website's `/api` belongs to that website.

The deployment remains one Docker image and one container. The API does not require PostgreSQL, Redis, a Node.js runtime or a Docker socket.

## 2. Common contract

### 2.1 Request conventions

- JSON field names: `camelCase`.
- IDs: opaque strings generated by the server; examples are illustrative.
- Times: RFC 3339 UTC, for example `2026-11-09T10:00:00Z`.
- Dates and charts may be displayed in `Asia/Dhaka`; storage and query timestamps remain UTC.
- JSON bodies use `Content-Type: application/json`; reject unknown fields.
- Omitted update fields remain unchanged; `null` clears a field only where explicitly allowed.
- Do not accept caller-supplied audit actors, timestamps, filesystem paths or computed status fields.
- Ordinary JSON limit: 1 MiB. Certificate upload: 1 MiB total. Restore upload: 256 MiB compressed, 1 GiB expanded, at most 10,000 entries. Reject excess with `413`.
- Generic JSON nesting limit: 32. Reject malformed JSON or duplicate object keys with `400`.

### 2.2 Success and errors

Single-resource response:

```json
{
  "data": {
    "id": "site_example",
    "name": "Demo Website",
    "version": 1
  },
  "meta": { "requestId": "req_example" }
}
```

Error response:

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "One or more fields are invalid.",
    "fields": [
      { "field": "domains[0]", "code": "INVALID_HOSTNAME", "message": "Enter a valid hostname." }
    ]
  },
  "meta": { "requestId": "req_example" }
}
```

| HTTP status | Meaning / stable error codes |
| --- | --- |
| 200 | Read or update succeeded |
| 201 | Resource created; return `Location` |
| 202 | Background job accepted; return job URL in `Location` |
| 204 | Delete or logout succeeded; no response body |
| 400 | `INVALID_JSON`, `INVALID_QUERY`, `UNKNOWN_FIELD` |
| 401 | `AUTH_REQUIRED`, `INVALID_CREDENTIALS`, `SESSION_EXPIRED` |
| 403 | `FORBIDDEN`, `CSRF_INVALID`, `ORIGIN_NOT_ALLOWED` |
| 404 | `NOT_FOUND` |
| 409 | `RESOURCE_IN_USE`, `DOMAIN_CONFLICT`, `APPLY_IN_PROGRESS`, `SETUP_COMPLETE`, `DRAFT_STALE`, `IDEMPOTENCY_CONFLICT`, `REAUTH_REQUIRED` |
| 412 | `VERSION_CONFLICT` |
| 413 | `PAYLOAD_TOO_LARGE` |
| 415 | `UNSUPPORTED_MEDIA_TYPE` |
| 422 | `VALIDATION_FAILED`, `CONFIG_INVALID`, `CERTIFICATE_INVALID`, `BACKUP_INCOMPATIBLE` |
| 428 | `PRECONDITION_REQUIRED` |
| 429 | `RATE_LIMITED`; return `Retry-After` |
| 503 | `NOT_READY`, `STORAGE_UNAVAILABLE`, `ACTIVATION_RECOVERY_FAILED` |

Never include shell output, SQL statements, secrets or stack traces in client errors. Return bounded, sanitized diagnostics and a request ID.

### 2.3 Pagination and filters

Collections use `limit` (default 50, maximum 200) and opaque `cursor`. Responses include `meta.nextCursor` (`null` when complete). Use stable ordering by creation time and ID; events order newest first. Reject cursors reused with different filters.

Event, metric and audit ranges use `from` inclusive and `to` exclusive. Default: previous 24 hours. Maximum event/audit range: 31 days. Reject `from >= to`. Exact totals are optional and must never be fabricated.

### 2.4 Concurrency and idempotency

Mutable resources return an integer `version` and a strong `ETag`, for example `"site_example-v3"`. `PATCH` and `DELETE` require the current `If-Match`; missing returns `428`, mismatch returns `412`. The comparison and write must be atomic.

Website, policy, exclusion, certificate and proxy-setting mutations increment a global `desiredGeneration` in the same database transaction. This generation is distinct from resource versions and configuration revision IDs.

Require `Idempotency-Key` on enrollment, configuration apply, rollback, backup creation and restore execution. Scope keys to principal and operation; enrollment uses the bootstrap identity. Retain the request digest and response for 24 hours. Same key and body returns the original result; changed body returns `409`. Never store plaintext credentials to implement idempotency. Enrollment retries must not mint additional sessions.

## 3. Authentication, sessions and roles

Use opaque server-side sessions, not browser-local JWT storage. Passwords use Argon2id. Validate password length from 12 to 128 characters and allow Unicode and spaces; do not silently truncate.

Production cookie:

```http
Set-Cookie: __Host-ariba_session=<opaque>; Path=/; Secure; HttpOnly; SameSite=Strict
```

Session defaults: 30-minute idle expiry, 12-hour absolute expiry. Rotate the session on login, reauthentication and privilege changes. Local HTTP development uses a separate development-only cookie name without `Secure`; refuse this mode on a non-loopback listener.

Before login or enrollment, `GET /auth/csrf` issues a short-lived pre-authentication binding cookie and returns a CSRF token. After login, obtain a new session-bound token. Every unsafe browser request, including login, enrollment, logout and multipart uploads, requires `X-CSRF-Token` and an exact allowed `Origin`. No GET endpoint changes state. Disable credentialed wildcard CORS.

Limit login to 5 failed attempts per account and client IP per 15 minutes, with additional bounded global rate limits. Use a generic invalid-credentials response. Never trust arbitrary forwarded IP headers.

| Capability | Admin | Operator | Viewer |
| --- | --- | --- | --- |
| Read websites, policies, metrics and redacted events | Yes | Yes | Yes |
| Edit websites, policies and scoped exclusions | Yes | Yes | No |
| Validate, apply and rollback traffic configuration | Yes | Yes | No |
| Read certificate metadata | Yes | Yes | Yes |
| Upload/delete certificates | Yes | No | No |
| Manage users, proxy destination allowlists, retention | Yes | No | No |
| Read management audit logs | Yes | No | No |
| Backup, download backup, restore | Yes | No | No |

Every endpoint requires authentication unless marked Public or Internal. Enforce roles on the server. No private-key download endpoint exists; backups are a separately protected exception.

## 4. Setup and account endpoints

| Method | Path | Access | Behavior |
| --- | --- | --- | --- |
| GET | `/setup/status` | Public | Return only `{ "enrollmentRequired": true }` |
| GET | `/auth/csrf` | Public/session | Return binding-specific `{ "csrfToken": "..." }` |
| POST | `/setup/enroll` | Bootstrap token | Atomically consume token and create first Admin; `201` |
| POST | `/auth/login` | Public | Authenticate, set session cookie and return user; `200` |
| GET | `/auth/me` | Any role | Current user and session expiry |
| POST | `/auth/reauthenticate` | Any role | Verify current password, rotate session, grant 5-minute recent-auth state |
| POST | `/auth/logout` | Any role | Revoke current session and clear cookie; `204` |
| POST | `/auth/password` | Any role | Verify current password, set new password and revoke all sessions; `204` |
| GET | `/auth/sessions` | Any role | List own redacted sessions |
| DELETE | `/auth/sessions/{id}` | Session owner | Revoke an owned session; `204`; no ETag required |

Enrollment request:

```json
{
  "enrollmentToken": "<single-use-token-from-local-cli>",
  "username": "admin",
  "displayName": "WAF Administrator",
  "password": "<administrator-chosen-password>"
}
```

Generate enrollment tokens only through a local CLI, expire them after 10 minutes, store their hash and disable enrollment after setup. Enrollment creates no session; proceed to login. Invalid and expired tokens share one generic error. Concurrent enrollment must create at most one initial account.

Login and reauthentication bodies use `username` + `password`, and `password`, respectively. Password change uses `currentPassword` + `newPassword`.

User management (Admin only): `GET /users`, `POST /users`, `GET /users/{id}`, `PATCH /users/{id}`, `DELETE /users/{id}`. Create accepts `username`, `displayName`, `role`, `password`. Patch accepts `displayName`, `role`, `enabled`; credentials are not ordinary user fields. Roles are `admin`, `operator`, `viewer`. Usernames are case-insensitively unique, 3–64 ASCII letters/digits/`._-`. Prevent disabling, deleting or demoting the last enabled Admin. Role changes or disable/delete revoke the target's sessions immediately. No remote password-reset endpoint is included in v1; document local recovery separately.

## 5. Websites

| Method | Path | Access | Result |
| --- | --- | --- | --- |
| GET | `/websites` | Any role | Paginated desired definitions |
| GET | `/websites/{id}` | Any role | Desired definition, version, active revision reference |
| POST | `/websites` | Admin/Operator | Create desired definition; `201` |
| PATCH | `/websites/{id}` | Admin/Operator | Update desired definition with `If-Match` |
| DELETE | `/websites/{id}` | Admin/Operator | Delete desired definition with `If-Match`; `204` |

Create example:

```json
{
  "name": "ERP Demo",
  "domains": ["erp.example.test"],
  "enabled": true,
  "listeners": { "http": true, "https": true, "redirectHttpToHttps": true },
  "certificateId": "cert_example",
  "policyId": "policy_detection",
  "upstreams": [
    { "scheme": "https", "host": "10.24.20.50", "port": 443 }
  ],
  "upstreamTls": {
    "verify": true,
    "serverName": "origin.example.test",
    "trustSource": "system"
  },
  "timeouts": { "connectSeconds": 5, "readSeconds": 60 }
}
```

Rules:

- Require 1–20 exact DNS hostnames per site; normalize IDNA and case. Wildcards are deferred in v1. Reject duplicate/conflicting enabled domain bindings.
- Require at least one listener; HTTPS requires a matching certificate. HTTP redirect requires both listeners.
- Require an explicit policy. New sites must reference a `detectionOnly` policy initially; later changes may select a `blocking` or `off` policy.
- Require 1–10 upstreams with `http` or `https` and ports 1–65535. Use round-robin routing for multiple upstreams in v1.
- Upstream TLS verification stays enabled in v1. Allow `system` trust or a stored CA bundle reference; private upstreams require a trusted CA rather than an insecure toggle.
- Validate destinations against Admin-controlled allowed CIDRs. Resolve hostnames and validate every destination at connection/re-resolution time; reject forbidden addresses and mixed allowed/forbidden answers. Deny metadata, management and unintended loopback destinations. Avoid validation-to-connect DNS gaps.
- Bound connect timeout to 1–30 seconds and read timeout to 1–300 seconds.
- `certificateId: null` is allowed only after HTTPS is disabled; `policyId` cannot be null.

Writes change desired state only. A disabled/deleted desired website can still be serving in the applied revision until a new revision succeeds. Responses must show `desiredGeneration`, `appliedRevisionId` (nullable) and `pendingChanges`. Determine active settings from revision details, not from the current editable row.

## 6. Policies and scoped exclusions

Policies: `GET /policies`, `POST /policies`, `GET /policies/{id}`, `PATCH /policies/{id}`, `DELETE /policies/{id}`. Read: all roles. Write: Admin/Operator. Updates/deletes require `If-Match`; referenced policies cannot be deleted.

```json
{
  "name": "Default Detection",
  "engineMode": "detectionOnly",
  "crs": {
    "paranoiaLevel": 1,
    "inboundAnomalyThreshold": 5,
    "outboundAnomalyThreshold": 4
  },
  "inspection": {
    "requestBodyEnabled": true,
    "requestBodyLimitBytes": 10485760,
    "requestBodyNoFilesLimitBytes": 1048576,
    "oversizeAction": "reject",
    "parserErrorAction": "reject",
    "responseBodyEnabled": false
  },
  "rateLimit": {
    "enabled": false,
    "requestsPerSecond": 10,
    "burst": 20
  }
}
```

Enums: `engineMode = off | detectionOnly | blocking`; `oversizeAction = reject | processPartial`; `parserErrorAction = reject | logOnly`. CRS paranoia level: 1–4. Anomaly thresholds: 1–100. Body limit: 1 byte–100 MiB; non-file limit cannot exceed total. Rate: 1–10,000 requests/second; burst: 0–100,000. Reject unsupported combinations.

`detectionOnly` records rule matches without ModSecurity enforcement. Nginx transport/body limits and rate limiting are separate controls and may still reject traffic. `off` disables ModSecurity inspection, not TLS/routing/limits. `processPartial` must surface incomplete-inspection status. Return warnings whenever configured semantics differ from what the tested engine can enforce. Server-side schemas reject unsupported inspection settings rather than silently ignoring them.

Exclusions are site-scoped resources:

| Method | Path | Access |
| --- | --- | --- |
| GET / POST | `/websites/{siteId}/exclusions` | Read all; create Admin/Operator |
| GET / PATCH / DELETE | `/websites/{siteId}/exclusions/{id}` | Read all; mutate Admin/Operator |

```json
{
  "ruleId": 942100,
  "path": "/search",
  "pathMatch": "exact",
  "target": { "collection": "ARGS", "name": "q" },
  "reason": "Approved search parameter false positive; change ticket CHG-001.",
  "enabled": true,
  "expiresAt": "2026-12-09T00:00:00Z"
}
```

Allow `pathMatch = exact | prefix` with documented path-boundary matching and `target.collection = ARGS | REQUEST_HEADERS | REQUEST_COOKIES`. Require a known rule ID, bounded exact target name and 10–1,000 character reason. No regex, raw directives or global rule-disable endpoint in v1. Use one documented path normalization consistently at validation and enforcement.

Optional expiry is UTC. The backend schedules and applies a new revision to remove an expired applied exclusion; the timestamp alone does not change Nginx. Expose `expiryRemovalStatus = pending | applied | failed` and alert on failed removal. Deleted/changed exclusions also require apply.

## 7. Certificates and trust bundles

| Method | Path | Access | Behavior |
| --- | --- | --- | --- |
| GET | `/certificates` | Any role | Metadata only |
| GET | `/certificates/{id}` | Any role | Subject, SANs, issuer, fingerprint and validity |
| POST | `/certificates` | Admin | Upload certificate chain/key; `201` |
| DELETE | `/certificates/{id}` | Admin | `If-Match`; reject if referenced by desired or active config |
| GET / POST | `/trust-bundles` | Read all; create Admin | Metadata / upload CA bundle |
| DELETE | `/trust-bundles/{id}` | Admin | `If-Match`; reject referenced bundles |

Certificate upload uses multipart fields `name`, `certificate` (PEM chain), `privateKey` (unencrypted PEM). Validate parsing, key match, validity, supported key algorithms and chain structure; site activation checks SAN coverage. Never log multipart content. Store keys using generated internal paths with restricted permissions. API-assigned IDs are the only file references.

CA upload uses multipart `name`, `bundle`; only public CA certificates, no private keys. `upstreamTls.trustSource = bundle` requires `trustBundleId`.

Rotation creates a new certificate ID, updates site references and applies a new revision. Management-listener certificate replacement and ACME automation are deferred; they are not implied by website certificate upload.

## 8. Configuration revisions and activation

| Method | Path | Access | Behavior |
| --- | --- | --- | --- |
| GET | `/configuration/status` | Any role | Desired generation, applied revision, pending changes, current job |
| GET | `/configuration/revisions` | Any role | Immutable snapshots and validation/activation metadata |
| GET | `/configuration/revisions/{id}` | Any role | Redacted typed snapshot and checksum; no keys/raw secrets |
| POST | `/configuration/revisions` | Admin/Operator | Snapshot desired state using `expectedDesiredGeneration`; `201` |
| POST | `/configuration/revisions/{id}/validate` | Admin/Operator | Queue render/test job; `202` |
| POST | `/configuration/apply` | Admin/Operator | Queue activation job; `202` |
| POST | `/configuration/rollback` | Admin/Operator | Queue activation of a retained known-good snapshot; `202` |
| GET | `/jobs/{id}` | Authorized role | Poll job progress and sanitized result |

Create revision: `{ "expectedDesiredGeneration": 12, "message": "Add ERP demo" }`. Atomically reject changed generations with `DRAFT_STALE`. Snapshots are immutable; validation and activation history are separate metadata.

Apply request:

```json
{
  "revisionId": "rev_example",
  "expectedDesiredGeneration": 12,
  "expectedAppliedRevisionId": "rev_previous"
}
```

Use `null` for `expectedAppliedRevisionId` before the first apply. Apply checks both expectations, verifies the snapshot matches the requested desired generation and revalidates under the current engine/CRS environment. Reject concurrent apply/rollback/restore with `409`.

```json
{
  "data": { "jobId": "job_example", "status": "queued" },
  "meta": { "requestId": "req_example" }
}
```

Apply stages: render → test Nginx/modules/rules → journal intent → atomically switch active revision → graceful reload → verify running revision and readiness → commit applied state. On failure, restore/reload the previous revision and verify recovery. Do not mark success solely because reload was requested.

Rollback body: `{ "targetRevisionId": "rev_known_good", "expectedAppliedRevisionId": "rev_example", "reason": "Unexpected application failures" }`. Revalidate old snapshots against the installed engine. Rollback updates applied state only; editable desired definitions remain unchanged and may show pending differences. The UI must display this explicitly.

Job representation:

```json
{
  "data": {
    "id": "job_example",
    "type": "configurationApply",
    "status": "succeeded",
    "stage": "complete",
    "result": { "appliedRevisionId": "rev_example" },
    "error": null,
    "recoveryStatus": "notNeeded",
    "createdAt": "2026-11-09T10:00:00Z",
    "finishedAt": "2026-11-09T10:00:02Z"
  },
  "meta": { "requestId": "req_example" }
}
```

Job status: `queued | running | succeeded | failed | interrupted`. Recovery: `notNeeded | pending | succeeded | failed`. Configuration jobs are readable by all roles; backup/restore jobs by Admin only. Jobs are durable. Reconcile activation intent after a restart before accepting another activation. A failed recovery makes readiness fail and exposes an Admin-visible incident. No generic shell, arbitrary file-edit or reload-command API is provided.

## 9. Security events and dashboard metrics

| Method | Path | Access | Behavior |
| --- | --- | --- | --- |
| GET | `/events` | Any role | Redacted transaction summaries |
| GET | `/events/{id}` | Any role | Redacted transaction with matched rules |
| GET | `/metrics/overview` | Any role | Windowed counters and freshness |
| GET | `/metrics/timeseries` | Any role | Bounded chart buckets |
| GET | `/audit-logs` | Admin | Management changes and outcomes |

Event filters: `from`, `to`, `siteId`, `action`, `ruleId`, `clientIp`, `limit`, `cursor`. Use exact filters in v1; no arbitrary SQL or regex queries. `action = allowed | blocked | rejected`; `blocked` means a confirmed WAF enforcement response, `rejected` means a separately classified transport/limit rejection. Unknown outcomes remain explicitly `unknown` in records rather than being inferred from rule matches.

```json
{
  "data": {
    "id": "evt_example",
    "transactionId": "tx_example",
    "timestamp": "2026-11-09T10:00:00Z",
    "siteId": "site_example",
    "appliedRevisionId": "rev_example",
    "engineMode": "detectionOnly",
    "clientIp": "192.0.2.10",
    "method": "GET",
    "path": "/search",
    "statusCode": 200,
    "action": "allowed",
    "inspectionComplete": true,
    "matches": [
      { "ruleId": 942100, "severity": "critical", "message": "SQL injection pattern detected" }
    ]
  },
  "meta": { "requestId": "req_example" }
}
```

This is an illustrative record, not evidence of a real attack. Return normalized path without query-string secrets, redacted rule messages, and no raw body, authorization header, cookies or matched secret values. A security-event listing is not a complete access log.

Metric definitions:

| Metric | Definition |
| --- | --- |
| `requests` | Unique completed access transactions from access telemetry |
| `blockedRequests` | Unique transactions confirmed blocked by the WAF |
| `detectedRequests` | Unique transactions with one or more security-rule matches |
| `ruleMatches` | Total rule matches; can exceed request count |
| `rejectedRequests` | Separately classified non-WAF limit/transport rejections |

Metrics include `from`, `to`, `generatedAt`, `ingestedThrough`, `lagSeconds`, `droppedRecords`, `availability` (`available`, `partial`, `unavailable`). Return `null` for unavailable counters, never fabricated zero. Use persisted deduplication and correlate access/audit records by transaction ID.

Timeseries accepts `interval = 1m | 5m | 1h | 1d`; cap at 1,000 buckets. Audit entries include actor ID, action, target ID, timestamp, redacted change summary, result and request ID. Never include password/key values.

## 10. System settings and health

| Method | Path | Access | Behavior |
| --- | --- | --- | --- |
| GET | `/system/version` | Any role | Product, schema, Nginx, ModSecurity and CRS versions |
| GET | `/system/health` | Any role | Components, readiness, storage and collector lag |
| GET / PATCH | `/settings/proxy` | Admin | Upstream allowed CIDRs and trusted proxy CIDRs |
| GET / PATCH | `/settings/retention` | Admin | Event, access-log, audit and backup retention |
| GET | `/health/live` | Internal only | Implemented: process responsive; no sensitive details |
| GET | `/health/ready` | Internal only | Implemented: currently `503 NOT_READY` until dependencies are configured |

Internal probes are bound to loopback and excluded from management/public proxy routes. User-facing detailed health requires a session. Liveness is independent of current proxy readiness.

Proxy settings are revisioned traffic configuration and require apply. Reject changes that invalidate referenced upstreams. Derive client IP only from configured trusted proxy chains; never accept a visitor-supplied header unconditionally.

Retention fields: `securityEventDays` (1–365, default 30), `accessLogDays` (1–90, default 7), `managementAuditDays` (30–730, default 180), `backupCount` (1–30, default 5), `maxLogDiskBytes` (100 MiB–100 GiB, default 1 GiB). Actual capacity remains bounded by available volume space. Validate free-space headroom. Changes affect cleanup workers after successful PATCH, not Nginx apply; return `effectiveAt`. Never silently remove all audit history on disk pressure.

## 11. Backup and restore

Admin only. Require recent reauthentication for backup creation/download and restore upload/validation/execution. CSRF applies to all unsafe requests.

| Method | Path | Behavior |
| --- | --- | --- |
| POST | `/backups` | Create consistent encrypted backup job; `202` |
| GET | `/backups` | Metadata only |
| GET | `/backups/{id}/download` | Stream encrypted artifact; no shared public download URL |
| DELETE | `/backups/{id}` | Delete completed artifact with `If-Match`; `204` |
| POST | `/restore-uploads` | Multipart encrypted backup upload; return staged ID; `201` |
| POST | `/restore-validations` | Validate upload and compatibility as a job; `202` |
| POST | `/restores` | Execute validated restore as a job; `202` |

Backup create body: `{ "passphrase": "<at-least-16-character-passphrase>" }`. Encrypt using a vetted authenticated-encryption backup implementation with a versioned format. The passphrase is write-only: never stored in job payloads, logs or idempotency records. If interrupted before encryption completes, fail the job and require a new request. No custom cryptography.

Use SQLite online backup and capture a matching configuration/secret snapshot. Backup includes private keys and user credential hashes; omit session/enrollment tokens and historical logs by default. Downloads use `Cache-Control: no-store` and `Content-Disposition: attachment`.

Validation body: `{ "uploadId": "upload_example", "passphrase": "<passphrase>" }`. Validate encryption, checksums, schema compatibility, archive path safety, expanded-size limits, certificate references and rendered configuration before returning a validation ID. Hold decrypted staged files in restricted storage for at most 10 minutes; do not persist the passphrase.

Restore body:

```json
{
  "validationId": "restore_validation_example",
  "expectedAppliedRevisionId": "rev_example",
  "confirmation": "RESTORE"
}
```

Serialize restore with all configuration writes and activations. Create a recovery checkpoint; stop/reconcile database writers, restore matching state and verify proxy configuration. On failure, recover the checkpoint and report recovery status. Successful restore revokes all sessions and requires login using the restored accounts. Restore job progress after session revocation is available only after authenticating as an authorized restored Admin; there is no public job-token bypass. Expired staging data is deleted automatically.

## 12. Local development integration

1. Run Go on loopback port 9000, using `./dev-data/ariba.db`.
2. Run Next.js on port 3000 and forward `/api/v1` through its development proxy.
3. Configure the exact allowed browser origin `http://localhost:3000` and explicitly enable loopback-only development cookies.
4. Use a separate Nginx/ModSecurity development container for traffic testing.
5. In this split setup, expose the activation executor as unavailable: validation/apply return `503` with `ACTIVATION_EXECUTOR_UNAVAILABLE` until the complete packaged runtime is running. Do not report simulated apply success.
6. Test integrated activation inside the final single container, where Go can invoke the constrained local configuration executor. No Docker socket mount is needed.
7. Build/export the dashboard; production uses static files and the Go API. No Next.js server actions or runtime API handlers.

Keep local database files, certificates, keys, cookies, bootstrap tokens and test logs out of Git. Include sanitized sample settings only.

## 13. Required implementation verification

- Enrollment is atomic, one-use and time-limited; no default credentials.
- Unauthorized requests, Viewer mutations, CSRF failures and origin mismatches are rejected.
- `If-Match`, generation checks and idempotency work under concurrent writes and retries.
- Website `/api` routes cannot reach the management API.
- DNS changes, forbidden destination addresses and management-loopback upstreams are rejected.
- Invalid rendered configurations cannot replace the last known-good active revision.
- Controlled traffic verifies DetectionOnly, Blocking, parser limits and accurate event attribution.
- Certificate mismatch, missing references, expired exclusions and restart during apply have explicit tested outcomes.
- Metrics count unique transactions correctly and expose stale/partial data.
- Logs and API errors do not disclose credentials, private keys or unredacted request secrets.
- Backup/restore is verified on a fresh instance, including session revocation and failed-restore recovery.

## 14. Deferred endpoints

ACME automation, GeoIP policies, IP reputation subscriptions, arbitrary custom ModSecurity rules, remote upgrades, API bearer tokens, multi-instance coordination and management TLS replacement through the browser are outside this v1 contract. Add each through an explicit versioned specification rather than placeholder endpoints that report success.
